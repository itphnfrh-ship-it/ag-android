# Задания бэкенду: API выгрузки круиза

Контракт для существующей системы, в которой уже лежат круиз, пассажиры и экипаж. Приложение CruisePass Verify в бою свой сервер не поднимает: забирает снимок по этому API и дальше ищет карту в локальной базе, в том числе без сети. Пока действующего API нет, репозиторий `ag-back` эмулирует этот контракт.

Приложение — просмотр записи. Эти методы ничего не меняют в статусах посадки и выхода. Методов записи нет.

Базовый путь всех методов: `/api/v1`. Кодировка JSON: UTF-8. Страница Swagger, с которой методы можно вызвать: [https://ag.system-rm.ru/swagger-ui.html](https://ag.system-rm.ru/swagger-ui.html). В Authorize указывается токен `emulator-port`. Имена людей, должность и номера отдаются как в источнике, без транслитерации и без смены регистра.

## Как клиент понимает «Онлайн» и когда качает данные

Клиент показывает **Онлайн** только если `GET /api/v1/status` вернул HTTP 200 и JSON `{"status":"ok"}`.

Любой другой исход — таймаут, обрыв, HTTP не 200, HTTP 200 без этого поля — **Офлайн**. Оператор статус руками не переключает. Недоступность одного круиза не делает устройство офлайн, если статус при этом отвечает `ok`.

Пока статус `ok` и устройство в Wi‑Fi, клиент сам выкачивает каждый круиз из списка в локальную базу вместе с фото. Повторно тот же `version` не качается. Мобильную сеть клиент для выгрузки не использует; серверу тип сети определять не нужно.

Смена `version` во время выгрузки отменяет новый пакет. Уже сохранённый на устройстве пакет остаётся рабочим.

`loadedAt` и время последнего считывания карты сервер не хранит и не отдаёт: это время устройства.

## Общие правила

Задание для всех методов ниже.

- Только HTTPS. Тело фото — байты картинки, не ссылка и не редирект на внешний URL.
- Заголовок данных: `Authorization: Bearer <токен устройства>`. Один и тот же токен на статус, список, манифест и фото. Выдача токена устройству в эти задания не входит.
- Неверный или пустой токен: HTTP 401 и тело `{"error":"unauthorized","message":"Требуется авторизация"}`. Клиент в этом случае показывает Офлайн.
- `Content-Type` JSON-ответов: `application/json; charset=utf-8`.
- Персональные ответы: `Cache-Control: no-store`.
- В журнале доступа сервера можно писать метод, путь, код ответа, `cruiseId`, `photoId`. Нельзя писать фамилии, имена, номера документов, даты рождения и байты фото.
- Неизвестные клиенту поля JSON он игнорирует. Переименование и удаление полей из этого контракта — новая `schemaVersion`.
- `version` — непрозрачная непустая ASCII-строка без кавычек и обратных слэшей. Клиент сравнивает её целиком. Меняется при любом изменении состава людей, их полей или байтов фото.
- `cardId` — строка. Ведущие нули и регистр значимы. В JSON это не число.
- Пустая строка не используется. Нет значения — `null`.
- Даты человека: календарные `YYYY-MM-DD`. Момент генерации снимка: RFC 3339, UTC, например `2026-10-15T06:00:00Z`.
- Ошибка, если не сказано иначе:

```json
{
  "error": "not_found",
  "message": "Круиз не найден"
}
```

`message` — короткая фраза для разработчика, без паспортных данных.

## Задание 1. Состояние сервиса

`GET /api/v1/status`

Лёгкий метод. По нему клиент рисует Онлайн или Офлайн. Ответ быстрее одной секунды, без обращения к фото и без персональных данных.

HTTP 200, только когда сервис готов отдать список круизов и манифесты. База, без которой выгрузка невозможна, лежит — не `ok`, а HTTP 503:

```json
{ "error": "unavailable", "message": "Сервис не готов отдавать данные" }
```

Успех:

```json
{ "status": "ok", "serverTime": "2026-10-15T08:00:00Z" }
```

`serverTime` — текущее время сервера, UTC. На решение Онлайн/Офлайн клиент смотрит только на HTTP 200 и `status == "ok"`.

Приёмка:

- Живой сервис с доступными данными отвечает 200 и `status: ok`.
- Выключенное хранилище данных отвечает 503, не `ok`.
- В теле нет пассажиров, экипажа и фото.

## Задание 2. Список круизов для устройства

`GET /api/v1/cruises`

Список уже отфильтрован по токену устройства: только те круизы, которые это устройство должно держать локально. Исторический флот целиком не отдавать. Клиент скачивает каждый элемент списка.

HTTP 200:

```json
{
  "schemaVersion": 1,
  "cruises": [
    {
      "id": "SZ-2026-14",
      "ship": "Astoria Grande",
      "name": "Восточное Средиземноморье",
      "version": "20261015T060000Z-3",
      "generatedAt": "2026-10-15T06:00:00Z",
      "currentPort": "Кушадасы",
      "paxCount": 1,
      "crewCount": 1,
      "photoCount": 1
    }
  ]
}
```

| Поле | Правило |
| --- | --- |
| `id` | Непустая строка, уникальна в списке. Пространство `cardId` у каждого круиза своё. |
| `ship` | Судно как в источнике. Идёт в шапку приложения. |
| `name` | Название круиза как в источнике. |
| `version` | Снимок данных этого круиза. |
| `generatedAt` | Когда источник собрал этот снимок. |
| `currentPort` | Текущий порт захода, как в источнике. `null`, если судно не в порту или порт в источнике не задан. |
| `paxCount` | Число записей `type = pax` в манифесте той же `version`. |
| `crewCount` | Число записей `type = crew` в манифесте той же `version`. |
| `photoCount` | Число записей, у которых `photo` не `null`, в той же `version`. |

Нет круизов для токена — HTTP 200 и `"cruises": []`. Это не офлайн.

Неизвестный путь круиза в методах ниже — HTTP 404, `error: not_found`.

Приёмка:

- Два устройства с разными токенами не обязаны видеть один и тот же список.
- Счётчики совпадают с манифестом той же `version`.
- Повторный вызов без изменений данных отдаёт ту же `version`.

## Задание 3. Манифест пассажиров и экипажа

`GET /api/v1/cruises/{cruiseId}/manifest`

Один JSON на весь круиз, без постраничной выдачи. Пассажиры и экипаж в одном массиве `persons`. Состав массива, поля и фото — один снимок `version`.

Заголовок запроса `If-None-Match: "<version>"`. Если эта версия и есть текущая, HTTP 304 и пустое тело. Иначе HTTP 200 и полный манифест. `ETag` ответа равен `"<version>"`.

HTTP 200:

```json
{
  "schemaVersion": 1,
  "cruise": {
    "id": "SZ-2026-14",
    "ship": "Astoria Grande",
    "name": "Восточное Средиземноморье",
    "version": "20261015T060000Z-3",
    "generatedAt": "2026-10-15T06:00:00Z",
    "currentPort": "Кушадасы"
  },
  "persons": [
    {
      "cardId": "001234",
      "type": "pax",
      "lastName": "Соколова",
      "firstName": "Анна",
      "rank": null,
      "documentNumber": "P-1001",
      "issuingCountry": "RUS",
      "nationality": "RUS",
      "dateOfBirth": "1984-03-12",
      "sex": "F",
      "expirationDate": "2030-11-01",
      "listNo": 1,
      "documentIssueDate": "2015-04-02",
      "photo": {
        "id": "ph-8f3a",
        "mediaType": "image/jpeg",
        "sha256": "2cf24dba5fb0a30e26e83b2ac5b9e29e1b161e5c1fa7425e73043362938b9824"
      }
    },
    {
      "cardId": "CRW-0042",
      "type": "crew",
      "lastName": "Иванов",
      "firstName": "Пётр",
      "rank": "Боцман",
      "documentNumber": null,
      "issuingCountry": null,
      "nationality": "RUS",
      "dateOfBirth": "1979-01-30",
      "sex": "M",
      "expirationDate": null,
      "listNo": 2,
      "documentIssueDate": null,
      "photo": null
    }
  ]
}
```

Хеш в примере иллюстративный. В ответе это SHA-256 байтов файла фото, 64 шестнадцатеричных символа в нижнем регистре.

`cruise.currentPort` — тот же текущий порт захода, что в списке круизов для этой `version`. `null`, если порта нет.

| Поле | Правило |
| --- | --- |
| `cardId` | Обязателен, уникален внутри круиза. Не обрезать нули, не менять регистр. |
| `type` | Только `pax` или `crew`. |
| `lastName`, `firstName` | Обязательны, непустые, как в источнике. |
| `rank` | У `crew` должность из источника или `null`, если в источнике её нет. У `pax` строго `null`. |
| `documentNumber` | Номер документа. Строка или `null`. Не число. |
| `cabin` | Номер каюты, как в источнике, или `null`. |
| `listNo` | Порядковый номер строки в списке-источнике, или `null`, если источник его не даёт. |
| `documentIssueDate` | Дата выдачи документа, `YYYY-MM-DD` или `null`. |
| `issuingCountry` | Страна выдачи документа, как в источнике, или `null`. |
| `nationality` | Гражданство, как в источнике, или `null`. |
| `dateOfBirth` | `YYYY-MM-DD` или `null`. Нереальная дата в снимок не попадает. |
| `sex` | Как в источнике, или `null`. Если источник кодирует пол, допустимы `M`, `F`, `X`. |
| `expirationDate` | Срок документа, `YYYY-MM-DD` или `null`. |
| `photo` | `null`, если фото нет. Иначе `id`, `mediaType`, `sha256` файла, который отдаёт задание 4. |
| `photo.id` | Непрозрачный идентификатор, безопасный для пути URL. Не равен обязательно `cardId`. |
| `photo.mediaType` | `image/jpeg` или `image/png`. |

Порядок `persons` не значим.

Снимок не отдавать, HTTP 422, если круиз нельзя выгрузить целиком: дубликат `cardId`, пустые обязательные поля, неизвестный `type`, нереальная дата, у члена экипажа нет должности, фото без файла или файл не того типа. Тело без массива людей:

```json
{
  "error": "inconsistent_snapshot",
  "message": "Манифест не собран",
  "details": [
    { "cardId": "001234", "reason": "duplicate_card_id" }
  ]
}
```

`reason`: `duplicate_card_id`, `missing_required_field`, `invalid_type`, `invalid_date`, `missing_rank`, `missing_photo_file`, `unsupported_photo_type`. В `details` только `cardId` и `reason`, без имён и документов.

Приёмка:

- `cardId` `001234` приходит строкой `"001234"`, не числом `1234`.
- Имя на кириллице, латинице или другом алфавите не перекодируется.
- Один и тот же `cardId` в двух круизах — две разные записи двух манифестов.
- Пассажир без фото: запись в массиве есть, `photo: null`.
- Дубликат `cardId` даёт 422 и не отдаёт половину списка.
- Повтор с тем же `If-None-Match` даёт 304.

## Задание 4. Файл фотографии

`GET /api/v1/cruises/{cruiseId}/photos/{photoId}?version={version}`

`version` обязателен и равен `cruise.version` манифеста, под который клиент качает файлы. Тело — сами байты изображения. `Content-Type` равен `mediaType` из манифеста. `Content-Length` обязателен. Редиректов нет.

Успех: HTTP 200 и байты, чей SHA-256 равен `photo.sha256` этой версии.

Ошибки:

| Ситуация | Ответ |
| --- | --- |
| Нет параметра `version` | 400, `error: bad_request` |
| `version` уже не текущая | 409, `error: version_conflict` |
| `photoId` нет в этой версии | 404, `error: not_found` |
| Круиз неизвестен | 404, `error: not_found` |

409:

```json
{ "error": "version_conflict", "message": "Версия круиза изменилась" }
```

Клиент после 409 или несовпадения хеша выбрасывает недокачанный пакет и оставляет прежний локальный. Сервер старую версию хранить не обязан, но текущие байты обязаны совпадать с хешем текущего манифеста.

Приёмка:

- Скачанный файл совпадает с `sha256` побайтно.
- Запрос без `version` не отдаёт картинку.
- После публикации новой версии запрос со старой `version` даёт 409, а не фото от нового снимка.
- В ответе нет JSON и нет URL.

## Задание 5. Согласованность выгрузки

Отдельная проверка поверх заданий 2–4.

- Список, манифест и фото одной `version` описывают одни и те же данные.
- Счётчики списка равны фактическому манифесту.
- Каждый непустой `photo` манифеста скачивается заданием 4, и хеш сходится.
- Пока клиент качает версию, публикация новой версии не подмешивает новые байты в старый `version`: старый запрос получает 409.
- Пустой круиз допустим: счётчики 0, `persons: []`, фото нет.

## Вне этих заданий

Не делать в этой очереди: дельту вместо полного снимка, поиск карты на сервере, запись факта считывания, смену статуса посадки или выхода, методы для истории просмотров. Поиск карта→человек выполняется на устройстве по локальной копии.
